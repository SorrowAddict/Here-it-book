# Testing Guide — Here-it-book

## 1. 기본 원칙

- 테스트는 가능한 경우 실제 도메인 명세와 API 명세를 기준으로 작성합니다.
- 중복 mock을 만들기보다 `src/mocks/handlers.ts`를 우선 재사용합니다.
- UI 상태는 먼저 Storybook으로 문서화하고, 이후 로직/상호작용 테스트를 보완합니다.
- 테스트를 삭제해서 실패를 숨기지 않습니다.

---

## 2. 기능 개발 기본 순서

새 기능 또는 변경 작업 시 가능한 경우 다음 순서를 따릅니다.

1. MSW 핸들러 추가/수정
2. Storybook 스토리 추가/수정
3. 기능 구현
4. Vitest / Storybook interaction test 작성
5. 필요한 경우 E2E 테스트 보강

---

## 3. 테스트 유형별 원칙

### Unit Test

대상:

- 커스텀 훅
- 유틸리티 함수
- 데이터 변환 로직
- 상태 계산 로직

도구:

- Vitest

규칙:

- Boundary Case(엣지 케이스)를 반드시 포함합니다.
- 입력값 누락, 빈 배열, 0개 데이터, 잘못된 상태 전환 등을 고려합니다.

### Integration / Interaction Test

대상:

- 컴포넌트 간 상호작용
- 버튼 클릭 후 상태 변화
- 로딩/에러/성공 상태 전환
- 상세 페이지의 LED 관련 사용자 시나리오

도구:

- Storybook `play` 함수
- `@storybook/test`
- `addon-vitest` 연동 환경

### E2E Test

대상:

- 라우트 간 이동
- 검색 → 상세 이동
- 사용자 기준 실제 흐름 검증

도구:

- Playwright

규칙:

- 모든 UI 변경에 E2E를 요구하지는 않지만, 실제 사용자 흐름에 영향을 주는 경우 검토합니다.

## 4. 기능별 검증 포인트

### 4.1 도서 검색

검증 대상:

- 검색어 입력 처리
- 페이지네이션 동작
- 정렬 동작
- 결과 목록 렌더링
- 빈 결과 상태
- 에러 상태

확인 포인트:

- `start`, `display`, `sort` 값이 요청과 UI 상태에 일관되게 반영되는지
- 검색 결과 카드/행이 요약 정보를 올바르게 렌더링하는지

### 4.2 도서 상세 조회

검증 대상:

- 상세 필드 렌더링
- 위치 정보 조합
- 지도 이미지 URL 처리
- 에러 상태 / 로딩 상태

확인 포인트:

- `section`, `floor`, `direction`이 UI에서 `section-floor-direction`으로 올바르게 조합되는지
- 검색 목록에서 사용하던 요약 정보와 상세 정보가 의미상 충돌하지 않는지

### 4.3 LED 점등/소등

검증 대상:

- ON 요청
- OFF 요청
- 버튼 상태 전환
- 중복 요청 방지
- 실패 상태 처리
- 자동 소등 반영 방식

확인 포인트:

- 점등 요청 중에는 중복 점등 요청이 막히는지
- 소등 요청 중에는 중복 소등 요청이 막히는지
- ON 상태에서만 OFF 액션이 가능한지
- 자동 소등이 외부 상태 변화라는 점을 깨뜨리지 않는지

### 4.4 수량 정보

검증 대상:

- `total_cnt`
- `borrowed_cnt`
- `available`

확인 포인트:

- 의미적으로 서로 모순되지 않는지
- UI에서 잘못된 계산이나 하드코딩이 들어가지 않는지

## 5. Storybook 작성 기준

재사용 UI 컴포넌트를 추가하거나 수정하는 경우, 필요한 상태를 Storybook으로 문서화합니다.

기본 상태 예시:

- `Loading`
- `Error`
- `Empty`
- `Success`

도메인 상태 예시:

- 검색 결과 있음 / 없음
- 상세 정보 로딩 / 성공 / 실패
- LED On / Off / 요청 중 / 실패

규칙:

- Story는 가능한 한 실제 API 명세 기반 mock을 사용합니다.
- 시각 상태와 사용자 상호작용 상태를 구분해서 보여줍니다.

---

## 6. MSW 재사용 원칙

- 테스트 코드에서 가능한 경우 별도의 중복 mock 정의를 만들지 않습니다.
- `src/mocks/handlers.ts`의 핸들러를 재사용합니다.
- mock 응답 구조는 반드시 API 명세와 일치해야 합니다.
- 검색 응답과 상세 응답을 섞지 않습니다.

---

## 7. 검증 명령어

기본 검증:

- `pnpm lint`
- `pnpm test:unit:run`

상황별 추가 검증:

- Storybook 확인: `pnpm storybook`
- E2E 테스트: `pnpm test:e2e`
